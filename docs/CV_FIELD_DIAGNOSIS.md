# CV 字段校验修复（2026-10-23）

## 复现证据

网页日志显示请求收到 HTTP 200 后，在 `evidence_validation` 阶段失败。旧日志未记录具体 ID，因此不能还原用户当次响应；没有读取或重发真实简历。本次用三份无个人信息的合成简历、原模型 `Qwen/Qwen3-8B` 和原端点真实复现了相同错误。

| 修复前合成输入 | 返回字段与位置 | 结果与耗时 |
| --- | --- | --- |
| 教育、技能、知识及重复提及的课程内容 | `education[0].field = Computing` | 未知 ID，CVError，HTTP 200，123.67 秒 |
| 两个学历及重复技能提及 | `education[0]` 和 `[1]` 均以 `Computing` 为 ID；`skills[0]` 和 `[1]` 均为 `skill_04` | 首先因未知教育 ID 失败，HTTP 200，4.15 秒 |
| 多项技能及项目内重复提及 | `education[0].field = Computing`；`skills[0]`、`[3]`、`[4]` 均为 `skill_04` | 首先因未知教育 ID 失败，HTTP 200，4.75 秒 |

`Computing` 是 `BACKGROUND['Current or completed field of study']` 的选项值，不是字段 ID。合法教育 ID 为 `Current or completed field of study` 与 `Highest/current study level`；技能为 `skill_01`–`skill_11`，知识为 `knowledge_01`–`knowledge_07`。

旧请求给出了正确白名单，但示例使用 `allowed education field`、`skill_XX` 等占位字符串，教育 ID 与选项的约束关系不够明确，也没有明确要求一个字段只能输出一次。真实模型把选项当 ID，并对重复提及输出多条技能记录。解析只是 JSON 解码，没有别名/大小写/多语言 ID 映射，也没有合并添加条目；失败由 `validate_extraction` 的未知/重复合并判断触发。

123.67 秒请求仍返回了有效 HTTP 响应；没有服务端历史日志，不能确定其等待时间原因，本次没有改超时或增加重试。

## 修复

- `src/cv_client.py`：从 `allowed_fields()`（来源为实际问卷 `BACKGROUND`、`SKILLS`、`KNOWLEDGE`）生成 JSON Schema。教育使用 `field.const` 与对应 `value.enum`，技能/知识使用合法 ID 枚举，明确字段类型、必填键、额外键限制和数组上限。Schema 作为准确的生成约定放入提示词；保持原服务的 `response_format=json_object`，不宣称服务端已强制执行 JSON Schema。
- 提示词要求每字段只输出一次、使用一段证据；教育最高学历取明确出现的最高等级，多专业无法单选时留待手填；`unconfirmed_fields=[]` 由客户端按实际已验证字段计算，避免模型猜测问卷缺失项。
- 精确相同的条目按字典全部内容相等去重，在去重前不以原始数组长度误判超限。每个唯一字段仍必须属于该组合法白名单，因此技能/知识/教育唯一字段数受实际问卷限制；经历仍保持 4 条上限。
- 不进行猜测式 ID 映射。未知 ID 明确失败；同字段不同值或不同证据明确报告冲突，不选首条或末条覆盖。原文证据、类型、选项及能力分校验保持生效。
- 日志区分 unknown / identical_duplicate / conflicting_duplicate，包含分组、零基数组位置和首次位置。合法字段 ID 可记录；未知的任意模型字符串用 `<unknown>` 隐去，只允许固定数字 ID 形状进入日志，防止输出 CV 文字。
- `src/locales/{en,ms,zh}.json`：新增独立的未知字段和冲突条目提示。
- `tests/test_cv_intake.py`：覆盖真实根因 Computing 被用作 ID、合法 ID/选项与问卷一致、正常响应、未知/错误组/大小写/显示名称不猜测映射、相同条目去重、冲突值/证据拒绝以及失败后保留上传和同意、可手动重试且不自动请求。
- `scripts/check_cv_service.py`：扩展真实合成 PDF 验证，包含人工自评、确认前不写画像、确认后才写画像。

## 部分信息提取修复与复核

“AI 提取结果缺少必填字段”的直接触发点是 `validate_extraction()` 对五个顶层分组的齐全检查，不是 `scoring_errors()`。旧逻辑拒绝省略空分组的响应，虽然分组本来就可以为空。这与完整问卷业务必填无关，但误伤了合法的部分提取。

现在响应仍必须是对象，至少有一个合法内容分组；允许省略其余分组，在客户端规范化为空数组，不产生任何问卷默认答案。存在的分组必须为数组，单条记录的字段/值/证据、未知 ID、冲突、类型和证据核验仍保持。未知顶层键、空对象、显式 null、损坏 JSON、PDF 无文字等继续独立报错。合法但没有匹配信息的空数组响应进入原确认页，说明继续问卷补充；模型提供了条目但全部无证据则仍明确报告不可核验。

复用原确认页、`apply_cv_fields()` 和问卷：确认前不写画像；只合并用户确认且非 None 的值，缺失分组和未选自评分不覆盖已有答案；应用后返回背景页，按原步骤补填。完整能力/兴趣检查仍在问卷第 5 步进入总确认前及第 6 步执行，列出缺项后才允许生成推荐；没有改动评分或推荐算法。

修改文件：`src/cv_client.py`（可选分组契约及规范化）、`src/cv_intake.py`（无匹配事实的正常提示）、三语言 catalog、`tests/test_cv_intake.py`、`scripts/check_cv_service.py`（新增 `--partial` 真实验证模式）。
