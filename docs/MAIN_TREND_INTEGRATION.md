# 主推荐链接入 GitHub 趋势快照

## 行为与边界

已确认画像 → 读取三个职业的有效缓存快照 → `evidence_ranking()` → 原 `rank_roles()` → 主结果页 → 用户选择职业 → 原 `build_plan()`。

- 默认选中 GitHub snapshots，不会在进入页面时发 HTTP。缺失或失效证据不以合成计数补齐；用户需显式选择 Synthetic demo 才使用合成趋势。
- 继续使用三个现有职业、原 topic 映射、原评分规则。`P` 为个人适配，`T` 为技术活动，Moderate 为 `0.85P+0.15T`，Fast 为 `0.65P+0.35T`。页面展示综合分以及相对 P 的趋势调整 `λ(T−P)`，并明确两权重是假设，不是概率或岗位预测。
- 职业要求、重要性、角色兴趣仍为合成值，职业链接只证明官方名称/代码。官方 O*NET 质量阻断仍由原重评函数执行，在主结果页保留质量边界。
- GitHub 统计公开、非 fork、新建仓库的两个完整 90 天窗口，仅是技术活动代理。查询来源、窗口、原始计数、获取时间和过期状态可追溯。
- 读取已有缓存与刷新复用原客户端。显式刷新一个职业，完整获取成功才替换快照；匿名每分钟最多 10 次尝试，15 分钟内复用缓存，无自动重试。来源校验和过期判断复用同一实现。
- 会话固定已读快照，直到用户明确刷新；即使保留快照超过 TTL，也会按当前时间显示过期，而不继续显示加载时的旧新鲜状态。
- 刷新不修改画像、已选职业、固定职业缺口、任务内容或进度。更高排名的职业可由用户点击确认切换；职业下拉选项使用稳定顺序，避免排名变化触发控件重置。
- 无完整趋势分的职业仍能提供明确标识的合成能力缺口和练习，但不能声称有完整证据匹配分。排名仅覆盖完整可用职业，页面明确披露覆盖数。

## 状态与兼容

主页面准确结果保存于 `pathway_assessment.recommendation_rows`，来源为 `recommendation_source`，证据为 `recommendation_snapshots`。主排名、分项解释和计划入口使用同一组 rows。

原 `rows` 和 `trends` 保留为固定合成基线，供原画像重评和计划文件校验使用。画像重评放在明确标识的合成基线折叠区。计划下载仍保存该合成基线及练习任务，不保存当前 GitHub 排名/快照，页面已告知；恢复后需要重新读取/刷新趋势证据。没有改变计划资源、SDG、评分公式或职业数量。
